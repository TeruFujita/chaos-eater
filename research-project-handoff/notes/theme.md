## いま関心があること（仮）

- Kubernetes / IaC 上の Chaos Engineering を、多 LLM エージェントで自動化する先行研究（ChaosEater）
- 「全部 LLM」ではなく、**どの工程に LLM を残すとコストが動くか**（配置・設計空間）
- 検証（VaC）や障害注入をコード／fixture に置き、直し（再構成）だけ Large LLM に残す案

## 素朴な疑問（並べるだけ）

- 「安くなった」だけだと何が言えるか。主語を「ChaosEater 改良」ではなく「LLM をどこに置くか」に上げられるか
- 検証・注入を固定するのは統制か、カンニングか。直しのゴールデンパッチ先出しとの線引きはどこか
- Kubernetes が Pod を戻すことと、Desired State を強くする「improvement」は同じではない、という理解で評価は足りるか
- 全部一気に置き換えると「何が効いたか」が消える。ablation（C0 / 途中 / C4）の最小セットは何か
- 小型 LLM・カスケードは今回切ってよいか（方針上は切る）

## 仮の主張（いまの一文）

同じ題材で、役割ごとの LLM をコード／テンプレに対応づけて置き換え、**直しだけ大型 LLM** を残した配置（C4）を公式全部 LLM（C0）と比べる。主スコアは呼び出し・トークン・$。成功はゲート。クリティカルは「どの役割を切ると効くか」。
